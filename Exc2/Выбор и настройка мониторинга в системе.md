Мониторинг предлагается настроить с помощью инструмента Prometheus.

Prometheus собирает данные по метрикам с экспортеров и/или получает из OpenTelemetry (на Схеме показана реализация, когда для БД используются экспортеры, а с АПИ и фронтенд компонентов данные собирает OTel).

Мониторинг производительности компонентов системы - методом RED (подходит для веб-сервисов, очередей и запросов к БД). Позволит определить узкие места в системе, из-за которых компания теряет заказы и, как следствие, клиентов. Ключевые метрики:

    Response time (latency) for shop API
    Response time (latency) for CRM API
    Response time (latency) for MES API

    Number of HTTP 200 for MES API
    Number of HTTP 200 for CRM API
    Number of HTTP 500 for MES API
    Number of HTTP 500 for CRM API

    Number of queue messages for RabbitMQ
    Number of queue messages for MES API
    Average waiting time for a message in a queue for RabbitMQ 

    Message Processing Rate for MES API
    Message Processing Time for MES API
    Error rate for MES API
    API Response Time for MES API

    Message Consumption Rate for MES API from RabbitMQ
    Message Consumption Rate for CRM API from RabbitMQ

    DB Query Latency for shop db
    DB Query Latency for MES db
    DB Queries per Message for shop db
    DB Queries per Message for MES db
    DB Error Rate for shop db
    DB Error Rate for MES db
    DB Read/Write Throughput for shop db
    DB Read/Write Throughput for MES db

Мониторинг показателей системного уровня - методом USE. Позволит вовремя среагировать на недостаток hw-ресурсов и применить масштабирование. Ключевые метрики:

    CPU % for shop API
    CPU % for CRM API
    CPU % for MES API
    Number of requests (RPS) for shop API
    Number of requests (RPS) for CRM API
    Number of requests (RPS) for MES API
    Memory Utilisation for MES API
    Memory Utilisation for shop db 
    Memory Utilisation for MES db 
    Memory Utilisation for RabbitMQ 
    Number of connections for shop db 
    Number of connections for MES db 
    Size of shop db 
    Size of MES db 
    Size of S3 storage

Мониторинг показателей бизнес-уровня - методом USE, так как нам важно отслеживать объем отложенной работы (Saturation) и ошибки. Метрики:

    Number of orders in queue for MES API - число заказов, ожидающих расчета стоимости. Ярлык - polygon_count, отображающий суммарное число полигонов в этих заказах.
    Average calculation time (calc_time \ polygon_count) for MES API - среднее время расчета стоимости a.k.a. compute rate
    Number of failed calculations for MES API
    % of direct orders - чтобы оценить какая часть compute ресурсов уходит на расчет заказов B2B сектора
    % of memory used for calculation - т.к. MES API отвечает не только за расчет стоимости, но и выполняет ряд других функций, следует оценить импакт этих функций

По следующим метрикам можно формировать EOD \ EOM \ EOY отчеты, которые наглядно покажут качество работы системы и станут дополнительным инструментом мотивирования senior management-а.  

    Number of submitted orders
    Number of approved orders 
    Number of started orders
    Number of completed orders
    accept_time - среднее время нахождения заказа между состояниями manu_approved и manu_started 

Общие статистические метрики:
    Average manufacturing time - среднее время создания изделия
    Average polygon count - среднее число полигонов в заказе (зная темпы роста числа заказов, можно спрогнозировать момент нехватки ресурсов)


*План действий* 

Если обнаружены очереди на обработку заказов на стороне MES API, варианты решения следующие:
    - добавить дополнительный инстанс MES API 
    - создать отдельный кластер с инстансами MES API, который будет обрабатывать исключительно запросы B2B сектора (но сперва нужно проанализировать соответствющие метрики)
    - вынести из MES API в отдельный сервис логику назначения ордеров на операторов и\или вывода списка ордеров

Если обнаружен недостаток ресурсов системного уровня, применяем вертикальное и\или горизонтальное масштабирование баз данных

Если число approved\started заказов не совпадает с числом submitted - анализируем результаты трейсинга и принимаем решения на основе этого анализа
